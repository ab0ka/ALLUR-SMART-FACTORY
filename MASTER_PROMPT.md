# Мастер-промпт Claude Code: Allur Smart Factory MVP

Ты — ведущий full-stack инженер. Доведи локальный Windows-проект до рабочего сквозного демо кейса №2 Allur Smart Factory. Приоритет — запуск и демонстрация к ближайшей полуночи, а не сложная графика. Работай в текущем репозитории, сначала прочитай структуру, package.json, README, AGENTS.md/CLAUDE.md и тесты. Не удаляй существующие файлы, не переписывай работающую архитектуру без необходимости. Если MVP уже реализован, проверь требования ниже и исправь только пробелы. Не ограничивайся планом.

## Контекст и честность
- Нет реальных производственных данных, телеметрии, CAD и полного официального текста задания. Все станции, мощности, события, план, метрики, прогнозы и геометрия СИНТЕТИЧЕСКИЕ. Не выдавай предположения за характеристики завода Allur.
- Постоянный видимый бейдж «Синтетические данные». Карта — условная схема, не CAD и не цифровой двойник действующего предприятия.
- Русский интерфейс для начальника смены. Цель: заметить отклонение → найти узкое место → изучить инцидент → увидеть изменение прогноза → получить объяснение → устранить инцидент.

## Минимальный результат
1. Интерактивная карта последовательных участков: сварка, окраска, сборка, контроль качества, отгрузка. Выбор участка, состояние, производительность и карточка OEE. Рабочая 2D SVG-карта обязательна; настоящее 3D необязательно и не должно задерживать сдачу.
2. Детерминированная симуляция смены 480 минут с фиксируемым seed, старт/пауза, шаг 5 минут, ускорение, сброс. Сервер владеет состоянием; браузер не рассчитывает доверенные метрики. Смена останавливается в конце. Никаких отрицательных счетчиков, двойных интервалов или NaN.
3. План-факт годного выпуска, отклонение, линейный план, график за смену. Различай всего обработано, годных, брак. Не суммируй один автомобиль по всем участкам в итоговый выпуск.
4. OEE = Availability × Performance × Quality. Availability = время работы / прошедшее плановое время; Performance = идеальное время цикла × всего / время работы; Quality = годные / всего. Обработай нулевые знаменатели. Укажи идеальный цикл и допущения. Исторические показатели не должны мгновенно изменяться при переключении сценария.
5. Качество: категории брака и доля годных. Журнал инцидентов: причина, участок, время начала/окончания, статус, действие устранения. Не выдумывай подтвержденные причины.
6. Сценарии: остановка окраски, рост брака, замедление сборки. Они должны влиять на симуляцию, метрики и прогноз, а не только на цвет. Устранение возвращает будущие параметры, сохраняя историю потерь. Запрети дубли активных инцидентов одного типа.
7. Объяснимый прогноз годного выпуска на конец смены с формулой, факторами и величиной дефицита; диапазон — эвристические ±10% будущего выпуска, НЕ доверительный интервал и НЕ обученная ML-модель. Покажи узкое место и рекомендации, привязанные к активным инцидентам. Цифры вычисляет код. LLM только объясняет готовый снимок.
8. NVIDIA AI API только через сервер: POST https://integrate.api.nvidia.com/v1/chat/completions; модель по умолчанию meta/llama-3.3-70b-instruct, настройка NVIDIA_MODEL. Ключ NVIDIA_API_KEY только в серверном окружении/.env. Не читать и не выводить реальные секреты, не помещать ключ в клиент, URL, логи, git или артефакт сборки.
9. Graceful fallback: без ключа, timeout, отказ сети, 401/429/5xx, пустой/некорректный ответ → локальное объяснение с явным статусом и причиной. Ошибка AI не должна ломать производство. Ответ NVIDIA отображать как обычный текст, без HTML.
10. Защити локальный сервер: привязка 127.0.0.1, проверка Host/Origin, CSRF для POST, ограничение тела запроса, валидация действий, ограничение частоты AI и количества одновременных вызовов, timeout. Не принимать endpoint/ключ/произвольный prompt от браузера. Локальное демо не объявлять production-ready.

## Архитектура и исполнение
- Сохраняй существующий стек. В пустом проекте допустим Node.js >=22.13, ESM, нативный HTTP, HTML/CSS/JS/SVG без сторонних runtime-зависимостей. Это уменьшает риск Windows-установки и работает без интернета/ключа.
- Раздели движок симуляции, прогноз/метрики, NVIDIA-адаптер, HTTP, UI, сборку и тесты.
- Сделай адаптивный, визуально цельный промышленный интерфейс: темный фон, контрастные показатели, условная карта в центре, карточка участка, объяснимый прогноз, журнал. Клавиатурный доступ, видимые focus, понятные подписи и состояние загрузки/ошибок.
- npm run build создает только публичные клиентские файлы в dist, без .env и серверного кода. npm start запускает сервер. npm test проверяет смысловые инварианты и HTTP/AI fallback. Не скачивай пакеты без необходимости.
- Состояние можно держать в памяти с явным предупреждением о сбросе после перезапуска; база, авторизация, CAD, реальные датчики и модель ML вне scope.

## Приемка
- Без NVIDIA_API_KEY весь сценарий работает offline, AI возвращает локальное объяснение.
- Сценарий остановки снижает будущий выпуск, шаг времени отражает простой в A/OEE, устранение возобновляет выпуск. Брак меняет Q и категории; замедление меняет P.
- Прогноз объясняется воспроизводимой формулой; прошлые счетчики не меняются от самого нажатия сценария.
- Проверены: OEE на известных значениях, zero-time, fixed-seed повторяемость, конец смены, сценарии/устранение/сброс, total=good+rejects, сумма категорий=rejects, HTTP validation/CSRF/Host, секреты не попадают в ответ/сборку, успешный mocked NVIDIA, missing-key/timeout/network/401/429/500/malformed fallbacks.
- Выполни npm test и npm run build, затем smoke HTTP и браузерную проверку основных действий на desktop/mobile. Не заявляй непроведенные проверки.
- Создай README с точными PowerShell-командами, .env.example, сценарий DEMO.md на 3–5 минут, VALIDATION.md с фактическими результатами и ограничениями, .gitignore. Проверку реального NVIDIA API без предоставленного ключа отмечай как непроведенную.
- В финале: абсолютная папка проекта, команда запуска, что готово, результаты проверок и оставшиеся ограничения. Не выполняй публикацию, push или установку глобальных инструментов без отдельного запроса.

## План работы
1. Инвентаризация → 2. движок и тесты → 3. HTTP и AI fallback → 4. сквозной UI → 5. сборка и smoke → 6. демо и команды. Этот порядок — приоритет; при обнаружении готовых частей не пересоздавай их.

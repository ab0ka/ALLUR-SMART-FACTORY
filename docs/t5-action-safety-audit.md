Реализован независимый объём T5 на базе main 3773d1d. PR остаётся draft:

Все данные синтетические. Производственный движок и серверная защита не менялись.

## Изменения

- confirmAction отклоняет повторный вход до смены текста/регистрации обработчиков, а также не открывается во время производственного запроса.
- Подтверждение снимает все свои обработчики. Запоздавший close предыдущего диалога не отменяет новый; Escape отменяет действие.
- Выпуск задания и смена приоритета теперь показывают объект и последствия и требуют подтверждения. Параметры выпуска фиксируются до ожидания ответа пользователя.
- priority, hold и plan теперь получают requestId, как остальные команды движка.
- Существующий общий updating подавляет второй производственный запрос до завершения первого. Автоматических повторов после сетевой ошибки нет.

## Дополнительные производственные кнопки — проверка T5

`scripts/qa-t5-production-controls.mjs` запускается после build с PLAYWRIGHT_MODULE
(file URL к существующему Playwright) и T5_PORT=3032. Он создаёт собственный createApp
для каждого варианта, отказывается занимать чужой порт, закрывает свои серверы/Edge.
Fixture готовится методами настоящего Workshop до открытия UI; сам проверяемый эффект
запускается браузерной кнопкой. Это тест защит, а не повтор полного ремонта T6.
Новых библиотек и платных запросов нет. Отчёты — data/t5-controls-<timestamp>/report.json.

Проверены **7 вариантов при 1440 и 390 px — 14 комбинаций**:

- Диагностика pump_check из диспетчера — одна работа.
- Аварийная работа repair_generic из карточки W1 — одна работа.
- Перевод из карточки поста на естественно освободившийся параллельный сварочный пост — одно событие vehicle_transferred.
- Снятие A2 с загрузки из карточки поста — одно событие hold_changed.
- Решение diagnose_repair из сравнения — одно решение и одна работа.
- Предложение чата типа command (проверка с последующим ремонтом) — одна работа.
- Предложение чата типа decision (результат сравнения) — одно решение и одна работа.

Для каждой комбинации проверены Cancel и Escape: полная сериализация движка неизменна,
производственных POST нет. Внедрённые HTTP409 и обрыв соединения до отправки на сервер
не меняют движок; после обоих следующий запрос успешно выполняется. Затем настоящий
сервер применяет команду, а ответ задерживается: два быстрых намерения, два нажатия
подтверждения и повторные попытки в ожидании дают ровно один успешный POST и один эффект.
После завершения открывается и отменяется другое намерение (сброс) — блокировка снята.
Ошибок JavaScript нет. Код приложения не потребовал исправлений.

Копия фактического отчёта: docs/t5-production-controls-report.json.
HTTP409 здесь внедрён на браузерном сетевом слое для покрытия обеих API-веток;
реальный конфликт лимита с другим клиентом проверялся отдельным аудитом.
Потеря ответа после серверного commit и безопасный ручной повтор после такого
неопределённого результата не покрываются этим сценарием и остаются указанным выше ограничением.

## Гонка старого GET с завершённым POST

Воспроизведён дефект: refresh начинал GET, action/applyDecision успешно заменяли state,
после чего старый GET приходил при updating=false и возвращал UI к прежнему состоянию.
Четыре regression до исправления падали: выпуск, сброс (revision уменьшается), решение,
ложная ошибка соединения от старого GET после успешного POST.

Минимальный фикс в refresh: ответ/ошибка применяются только если текущий объект state
всё ещё тот же, что был при начале GET, и сейчас нет активного обновления/чата.
Сравнение identity не предполагает монотонность revision и работает при сбросе.
Новые поля движка, изменение контекста/черновика чата и автоматические повторы POST не добавлялись.

tests/refresh-race.test.mjs исполняет реальные refresh/action/applyDecision с управляемым
порядком ответов в VM. Все пять тестов проходят; обычный GET нового сервера с меньшей
revision и новым CSRF принимается, актуальная ошибка соединения остаётся видимой.
Полный npm.cmd test: **100/100**, build OK. После исправления повторно пройдены все
14 вариантов scripts/qa-t5-production-controls.mjs в Edge при 1440/390 px.
Сам порядок старого GET и POST детерминированно проверен в VM; браузерный прогон проверяет
совместимость производственных действий, а не выдаётся за отдельное воспроизведение этой гонки.
